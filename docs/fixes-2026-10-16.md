# 外部审查的四个问题（2026-10-16）

审查对象：`main` 分支提交 `20ff932`。四个问题都先写出复现测试，修正前失败、修正后通过；修正后各 crate 的全部测试照常通过。下面的结果来自虚拟时间仿真、假设备与单元测试，**不是实机结果**。

## 1. 嵌入式换曲时打开曲目阻塞主循环（P1）

**问题**：
- `FatStorage::open` 在每次打开前都沿整条簇链重新核对；
- 耗时随文件长度与碎片程度增长，FAT 读取只缓存一个扇区；
- 换曲时主循环被阻塞，设备持续取数，队列取空后欠载；
- 预填公式 `P ≥ U + D + T` 只覆盖稳定读取，没有计入打开。

**复现**：`qy-host-embedded/tests/embedded_sim.rs` 的 `opening_a_long_fragmented_track_does_not_underrun`。
- 两首 96 kHz / 24 位 / 双声道 WAV，第二首约 8 MiB；
- 测试按规范自行解析 FAT，把第二首的簇链打散，相邻两簇在 FAT 中相隔 257 项，每一跳都换 FAT 扇区；
- 每块读取 100 µs，时序核对通过；
- 修正前：欠载 521 次，缺失 133 248 帧（审查报告在其环境中为 94 次、23 928 帧，现象相同）；
- 修正后：无欠载，两首都与参考逐字节一致。

**修正**：
- **扫描时**：照常沿整条簇链核对每个文件（不在播放的实时路径上）。
- **打开时**：只重新读取目录项（换卡而未重新扫描时它可能已变），核对起始簇有效，不再走整条链。耗时只与根目录大小有关。
- **读取时**：每次读取前逐跳核对到本次要访问的位置，代价与跨过的簇数成正比，计入读取耗时 `U`（新增 `fatcheck::ChainCursor`，含 Brent 环路检测，状态跨读取保留）。
  - 换卡而未重新扫描时，无效表项、越界簇、坏簇标记与提前结束都在 `embedded-sdmmc` 走到那一跳之前报告损坏；
  - 新测试 `fat_corrupt.rs::chain_corrupted_after_scan_is_caught_while_reading` 覆盖这些情形。
- **定位**：只移动读取位置，下一次读取时核对到目标处。耗时随距离增长，但引擎定位时会停止设备并重新预填，只增加延迟，不造成欠载。
- **预填公式**：改为 `P ≥ O + U + D + T`。`O` 为打开一首曲目的最长耗时（板级实测），`Load` 新增 `open_us`，预填不足的报告写明各项。
  - QEMU 演示用名义值 10 ms；
  - 板级示例用未实测的占位值 20 ms，启动时打印警告。

**仍未覆盖**：
- **环路**：簇链在扫描之后被改成文件长度以内的环路时，读取可能先读出重复的簇才发现。读取有界（以文件长度为限）、不 panic，重新扫描时照常拒绝。原先打开前的整链核对能在打开时发现这种情况，但它的代价正是本问题。
- **大块元数据**：下一首的文件头阶段若要读过很大的元数据（例如 FLAC 中内嵌的大幅图片，解码器按顺序读过，不定位跳过），读取量取决于文件本身，没有板级常数上界，换曲时仍可能欠载（照常计数与报告）。改为定位跳过可以把代价降到按簇查表，另行处理。

## 2. FLAC 没有核对帧号 / 样本号的连续性（P2）

**问题**：
- 帧头的编号已解析，但没有与已解码的内容核对；
- RFC 9639 §9.1.5 规定：固定块策略下为此前的帧数，可变块策略下为此前的样本数；
- 交换两个完整音频帧时，每帧的 CRC 都仍然正确，总样本数也不变，于是照常播完并记为严格路径。

**复现**：`qy-codec-flac/tests/behavior.rs` 的 `frame_numbers_must_follow_decoded_content`。
- 夹具：一个固定块流（flac 命令行）与两个可变块流（手写，含有定位表 / 无定位表）；
- 改动：交换前两帧、重复第一帧、去掉第二帧；
- 修正前照常解码，修正后按不合规拒绝。

**修正**：
- 解码器记录下一帧应有的编号：从 0 开始，每帧之后按帧号加 1（固定块）或样本号加块大小（可变块）推进；
- 不符时拒绝，明细为新增的 `FlacError::FrameNumberMismatch`（`DecodeError::Malformed`）；
- 定位后由落点之后的第一帧重新确定编号，此后照常核对；
- 原有的 FLAC 测试全部通过，包括 libFLAC 逐样本核对与 12 600 次定位。

## 3. 浮点拒绝记录跨设备沿用（P2）

**问题**：
- 引擎记下“当前设备不接受某浮点格式、已改为转换”，相邻同格式曲目据此续用整数设备；
- 这个记录没有在停止与新的播放开始时清除；
- 桌面图形界面跨播放会话复用同一组宿主资源，换到另一台接受浮点的设备后仍直接转换（降为整数，样本已改变）。

**复现**：`qy-player` 的 `float_rejection_does_not_outlive_session`。
- 同一组资源先在只接受整数的假设备 A 上转换播放浮点；
- 再在接受 32 位浮点的假设备 B 上播放“16 位整数、同格式浮点”；
- 修正前第二首被转成 16 位整数，修正后按位原样送到浮点格式。

模拟宿主使用 `ReusePolicy::Identical`，不走这条续用路径；它的同类测试 `sim_float.rs::float_rejection_does_not_outlive_device` 修正前后都通过，作为该策略下的回归保留。

**修正**：停止与开始播放（含定位、切歌）时清除该记录。代价是同一次播放中定位或切歌后，浮点曲目会再向设备请求一次浮点格式。

## 4. 连续短曲目时状态缺少源格式（P2）

**问题**：
- 桌面播放器按解码顺序只保留最近 8 首的源格式；
- 引擎的队列最多容纳 8 个曲目边界，还可以再解析下一首；
- 短曲目连续播放时，正在播放的曲目的记录被挤掉，状态快照中的 `source` 为 `None`，界面的源格式行缺失。

**复现**：`qy-player` 的 `status_keeps_source_of_playing_track_with_many_short_tracks`。
- 20 首各 300 帧的 WAV，在按真实时间消费的假设备上播放；
- 修正前有设备已打开而 `source` 为空的快照，修正后没有。

**修正**：
- 不再按条数淘汰：记录新曲目时只淘汰已经播完的曲目，即只保留正在播放到正在解码之间的各首；
- 切歌后正在解码的曲目可能在前，此时只保留这两首；
- 保留的条数受引擎队列可容纳的曲目边界数限制。

## 同时完成：浮点 WAV 的 `fact` 可有可无

用户 2026-10-16 决定（RIFF 1991 原文只要求压缩格式有 `fact`），见 [f3-float.md](f3-float.md) §1：
- 没有 `fact` 时帧数按 `data` 长度计算；
- 有 `fact` 时必须与 `data` 一致。

ffmpeg 输出到管道的浮点 WAV（长度为占位值）现在可以播放，结构修正写入报告。

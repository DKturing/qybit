# R1 资源计划与可靠性验证：记录

日期：2026-10-14。任务卡：[tasks/R1.md](../tasks/R1.md)。本卡不需要硬件。下面的结果来自模拟、虚拟时间仿真、fuzz、QEMU 与开发机，**都不是实机结果**；MCU 的实时性与数字输出要到 M3 T3 在实物上验证。四个确定性约束的统一表述见 [arch-core-mcu.md §5](arch-core-mcu.md#5-确定性约束r1-5)。

## 1. 资源计划（R1 §1）

**接口形式（待定事项 1 的决定）**：在 `qy_core::engine` 新增可选 trait `Resources`，引擎的泛型约束改为 `D: Decoder + Resources`。冻结的 `Decoder` 不变。

理由：
- 需求查询只有引擎用得到，不属于逐块解码契约；
- 默认实现表示“无额外说明”，WAV 不需要改动；
- 只增加 trait、不改 `Decoder`，不会破坏冻结接口。

**行为**：
- 文件头阶段因本机解码容量不足的拒绝（FLAC STREAMINFO 的声道、最大块、声明的最大帧长）都换算成 `EngineFault::Capability`，与采样率、声道、位深、队列的检查同一类别、同一格式。新增两种原因：
  - `FlacBlock`：“FLAC 最大块 a 帧超出本机配置的 b 帧”；
  - `FlacFrame`：“FLAC 声明的最大帧 a 字节超出本机输入窗口 b 字节”。
- 6 声道 WAV 与 6 声道 FLAC 在 Embedded 配置下都报 `Capability(Channels { channels: 6, max: 2 })`。
- 32 位 FLAC 在 Embedded 上由已有的位深检查报 `Bits { bits: 32, max: 24 }`。
- **文件头声明不可信**：STREAMINFO 只用于提前给出原因与播放计划；逐帧边界检查保留。“STREAMINFO 声称小块、实际帧更大”的夹具仍在帧级以解码错误拒绝，不 panic。
- **播放计划** `Engine::plan()`：包括源格式、设备格式、预填帧数与时长、队列需求/容量、FLAC 声明的最大块与最大帧 / 本机容量。
  - 嵌入式宿主在设备打开后发出 `EVENT plan …`；
  - 桌面报告每个输出流写明“播放计划”。

**验收**：
- 回归摘要不变：WAV 1000 种子、FLAC 1200 种子，摘要不含拒绝原因。
- `sim_multichannel` 中 6 声道 FLAC 在 Embedded 上的期望由 `Core(Decode(CapacityExceeded))` 改为 `Capability(Channels { 6, 2 })`。依据是 R1 §1：同一资源原因归同一类别。
- MCU 演示第 4 首的期望按同一依据更新。

## 2. 缓冲水位统计（R1 §2）

**阈值**（代码常量，`qy_pcm_format::queue::Watermark::for_stream`）。各档互斥：

- 低水位：低于预填量的一半；
- 临界：低于 2 个输出周期（MCU 为 2 个 DMA 缓冲，桌面为 2 个渲染包或 2 个写周期）。

**观测点**：消费端每次取数前，且只在运行中、未暂停、未排空（桌面为未到 EOF）时观测，因此尾部排空与暂停静音不计入。每次观测只做常数次比较与加法。只观测，不改调度，不改变样本。

**报告位置**：
- 嵌入式：`STATUS … wm_min_frames= wm_min_ms= wm_low= wm_critical=`；
- 桌面：报告中的“队列水位”；
- A 层回环：JSON 的 `watermark` 字段；
- 模拟：输出段（不计入回归摘要）；
- QEMU 演示：状态行。

**虚拟时间仿真的数值**（`qy-host-embedded` 测试 `watermark_low_critical_and_underrun_order`）。仿真确定，当前代码下每次运行相同：

| 情形 | 磁盘时序 | 结果 |
| --- | --- | --- |
| 声明以内 | 每块 150 µs，每 40 块停顿 8 ms | 最低水位 10 869 帧（低水位线 5 512，临界线 512），低水位 0 次，临界 0 次，欠载 0 |
| 超出预填 | 每块 100 µs，每 300 块停顿 400 ms | 第一次欠载时已有临界 17 次、低水位 21 次；全程欠载 19 次 / 4 456 帧，状态行 `wm_low=20 wm_critical=4`（最后一段） |

这些数值随存储访问的块数变化。R1 §4 的 FAT 核对增加了块读取，最低水位由 10 741 变为 10 869 帧。

**其他观测**：
- **A 层回环**：最低水位为 `null`。夹具曲目很短，渲染循环开始前已全部入队（已到 EOF）。语义正确：EOF 后的取数不计入。
- **QEMU 演示**：`wm_critical=0`。
- **桌面端到端**：见 §6。

## 4. 损坏文件系统 fuzz（R1 §4）

**fuzz 目标**：`fuzz/fuzz_targets/fat_storage.rs`。

- **基础镜像**：两个有效镜像，FAT16 与 FAT32，由 `qy-fat-image`（`fatfs` 格式化）生成。各含 4 个文件：WAV、FLA、长文件名、空文件。
- **输入格式**：第 1 字节选择镜像，其后是补丁记录 `[偏移 3 字节][长度 1 字节][数据]`。
  - 偏移最高位为 1 时，补丁落在元数据区：MBR、引导扇区、FAT 表、根目录与数据区开头，按基础镜像的引导扇区算出；
  - 否则落在镜像前 8 MiB。
  - 补丁在块设备读取时叠加，不复制整块镜像。
- **每个输入的操作**：扫描 → 逐首打开并读完 → 重新扫描 → 再读第一首。
- **检查**：
  - 不 panic；
  - 块设备越界读取以 `Err` 返回；
  - 单个文件读取不超过 8 MiB，块读取总数不超过 400 万次；
  - 错误都以 `Err` 返回。

**发现的问题**：

- **问题**：`embedded-sdmmc` 0.10.0 在簇链遇到空闲表项 0 时 panic：`fat/volume.rs` 中 `cluster_to_block` 计算 `0 - 2` 时减法溢出。release 构建关闭溢出检查时会静默回绕，读错块。
  - 触发输入：`crash-82f0d370…`，把 FAT16 第 1 份 FAT 中一个表项的低字节改为 0。
  - 同一读取路径上，`next_cluster` 对越界簇号直接 `panic!`；簇链环路会让读取一直进行到声明的文件长度。
- **处理**：按 R1 §4 的处理顺序，在 `FatStorage` 层加防护。新增 `fatcheck` 模块，按 FAT 规范（Microsoft fatgen103）独立解析引导扇区、原始目录项与 FAT 表项，不信任 FAT 库的结果：
  - **挂载前**，核对 MBR 分区项与引导扇区：
    - 每扇区 512 字节；
    - 每簇扇区数为 1–128 的 2 的幂；
    - 保留扇区、FAT 份数、扇区总数、FAT 大小都非零；
    - 所有算术用 checked 运算；
    - 簇数 ≥ 4085（拒绝 FAT12）；
    - FAT 能容纳全部表项；
    - FAT16 的根目录项数非零；
    - FAT32 的根目录簇链每一跳有效、以结束标记终止、步数不超过簇数。
  - **扫描时**，读原始 32 字节目录项，核对每个文件：
    - 长度为 0 时不读数据；
    - 起始簇在 `2 ..= 簇数 + 1`；
    - 前 ⌈长度 / 簇字节数⌉ 个簇每一跳有效；
    - 整条链无环路：步数以簇数为上界，另用 Brent 算法提前发现环路。
  - **打开与读取时**（2026-10-16 修改，原先打开前沿整条链重新核对，耗时随文件长度与碎片程度增长，换曲时阻塞主循环、造成欠载，见 [fixes-2026-10-16.md](fixes-2026-10-16.md) §1）：
    - 打开时只重新读取目录项（起始簇有效）；
    - 每次读取前逐跳核对到本次要访问的位置（`fatcheck::ChainCursor`，含环路检测），代价与读取跨过的簇数成正比；
    - 覆盖“换卡而未重新扫描”的情况：无效表项、越界簇、坏簇标记与提前结束都在 `embedded-sdmmc` 走到那一跳之前报告损坏；环路在文件长度以内时可能先读出重复的簇才被发现（有界、不 panic），重新扫描时照常拒绝。
  - **不合格时**：
    - 单个文件跳过，计入 `FatStorage::corrupt_entries`；
    - 整卷损坏时返回 `FatError::Corrupt`。
    - 这两种情况都不交给 FAT 库。
- **上游**：这些防护在本层已能完全拦下，因此不需要评估其他 FAT 库（待定事项 2）。`cluster_to_block` 与 `next_cluster` 对损坏表项缺少范围检查，这个问题尚未向上游报告；是否报告由用户决定。

**回归用例**：`crates/qy-host-embedded/tests/fat_corrupt.rs`。FAT16 与 FAT32 各跑一遍；损坏位置由测试按规范独立解析得到，不依赖 `fatcheck`。覆盖：

- 完好镜像；
- 簇链遇空闲表项（fuzz 发现的问题）；
- 起始簇为 0、1 或越界；
- 簇链指回自身、坏簇标记、提前结束、指向越界簇；
- 链中间环路、尾部环路；尾部表项为空闲时照常接受，并读出正确内容；
- 文件长度大于卷；
- 引导扇区的各字段损坏；
- FAT32 根目录链环路与起始簇 0；
- 打开前重新读取目录项；
- 扫描之后簇链被改坏：读取时逐跳发现（`chain_corrupted_after_scan_is_caught_while_reading`）。

**fuzz 记录**（开发机见 §6.1，`cargo +nightly fuzz`，libFuzzer，`-fork=4`）：

| 运行 | 版本 | 时长 | 执行次数 | 覆盖 / 特征 / 语料 | 结果 |
| --- | --- | ---: | ---: | --- | --- |
| 初次 | 仅 FAT16，无防护 | 未记录（发现崩溃即停止） | 未记录 | 未记录 | 发现上述 panic（`crash-82f0d370…`） |
| 第一轮 | 仅 FAT16，有防护，尚无环路判定 | 约 3 分钟（中途停止，改用最终版本） | 约 43 万 | 1695 / 2638 / 165 | 0 崩溃 |

## 6. 桌面吞吐基准（R1 §6）

### 6.1 机器与构建

- CPU：Intel Xeon Processor @ 2.10GHz，4 个 vCPU，每核 1 线程，KVM 虚拟机（云端会话容器）；
- 频率策略：不可读（虚拟机未暴露 cpufreq）；
- 系统：Linux 6.18.44；
- 工具链：rustc 1.97.0；
- 编译选项：工作区默认 release 配置（opt-level 3，未开 LTO，codegen-units 默认 16），未设 `target-cpu`。

**结论只对这台机器成立**，不能代表用户的桌面，更不能代表 MCU。另外，云端虚拟机的计时会受同机负载影响，因此表中同时给出最慢一次和中位数。

### 6.2 测试文件

- **生成**：由 `qy-gen-fixtures` 的基准生成器（`qy_gen_fixtures::bench`）按固定种子生成，内容确定。
- **样本**：每声道一条带惯性的整数随机游走，加几个最低位的噪声。不用浮点三角函数，跨平台逐位相同。
- **FLAC 编码**：由同一模块按 RFC 9639 编写：
  - 各声道独立编码（不做立体声去相关）；
  - 预测器为固定 2 阶，或 LPC 32 阶（精度 15 位、移位 12）；
  - 分区 Rice，每分区按平均值选参数。
- **独立核对**：编码器与 libFLAC 交叉核对，测试 `tools/qy-bench/tests/encoder_libflac.rs`。用 Xiph flac 1.4.3 解码 16 个文件，覆盖 16/24/32 位、2/8 声道、44.1–384 kHz、块 4096/16384、固定与 LPC32，样本全部与源相等。
- **压缩率**：比真实音乐差。16 位约为原始大小的 48%，32 位约 74%。残差越大，Rice 解码越慢，因此这里的 FLAC 速度应偏保守。

- pack 到 WASAPI 独占常用格式：16 位 → C16/V16，24 位 → C32/V24（左对齐），32 位 → C32/V32；

### 6.4 端到端余量

**命令**：`cargo run --release -p qy-bench -- e2e --seconds 10`。

**链路**：
- 播放器层：`qy_player::play_source`，新增的曲目来源接口，用法与 `play` 相同；
- 其后依次是：引擎 → 自有解码 → pack → `rtrb` 队列 → 真实的整包渲染循环；
- 假设备新增 `FakeDevice::Clock`：按真实时间消费，每 10 ms 发出一次事件、取一包。渲染线程迟到时不补发事件，迟到期间队列不足照常记为欠载。

**设置**：
- 假设备接受 C16/V16、C24/V24、C32/V24、C32/V32，协商取有效位数够用的最小容器。因此 24 位源用 C24。
- 桌面配置档队列为 3 072 000 字节，表中给出该设备格式下的队列时长。
- 读取延迟注入在曲目读取层（`MemSource`）：每次读取固定延迟，或每读过若干字节停顿一次。

**核对方式**：
- 设备收到的数据去掉欠载补入的静音后，与独立 pack 的参考逐字节比对。欠载明细超过保留的 64 条时无法去掉静音，如实标记“未比对”。

### 6.5 结论（P1 第 3 项的依据）

- **全部规格都达到实时**：解码 + pack 的最慢一次都在 7× 以上。
- **余量最小**：8 声道、LPC 32 阶的 384 kHz FLAC，最慢 7.8–9.4×，即单核约 11–13% 的时间。其次是 8 声道固定预测的 384 kHz FLAC（13–15×）与 8 声道的 192 kHz FLAC（16–33×）。
- **按“不到实时或余量很小”的标准**：这台机器上没有达不到实时的规格。余量最小的是上面这组 8 声道高采样率 FLAC。
- **对 P1 的建议**：
  - 第 3 项（解码内核优化）在桌面上暂无必要启动；
  - 如果 M3 T3 的 MCU 实测显示 FLAC 负载偏高，优先看 LPC 高阶预测与 Rice 解码这两段；
  - 是否启动由 M3 T3 的数据决定。
- **端到端**：
  - 在队列允许的规格内，不注入延迟或每次读 5 ms 时没有欠载，最低水位等于预填量；
  - 停顿超过队列时长时，水位统计先报临界，再报欠载。
  - 桌面的瓶颈是配置档的队列容量，不是解码速度：384 kHz / 8 声道因队列不足被拒绝。是否扩大桌面队列属于配置档决定，不在本卡范围。

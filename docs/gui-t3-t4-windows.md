## 1. 界面上显示什么、来自哪里

| 区域 | 内容 | 来源 |
| --- | --- | --- |
| 格式行（工具栏下方） | 正在播放的曲目的源格式 → 设备流格式（独占协商结果）；未播放时为空 | `Status::source`（按正在播放的曲目查找，不是已预读的下一首）、`Status::device` |
| 状态栏第一栏 | 播放标记（▶ / ‖）、曲目序号、已播放 / 总时长、欠载次数（缺失帧数）、因错误跳过的曲目数；播放结束后为结论 | `Status`；结束后为 `Outcome`（来自播放器报告） |
| 状态栏第二栏（只在播放中） | 保真状态，按优先级：有欠载 → 有曲目跳过 → 声道已改变（单声道复制） → 软件路径未改动样本 | 同上 |
| 日志 | 每次播放开始时的单声道复制选项状态；曲目开始；设备流协商记录（源格式、每次请求的格式与描述类型和 HRESULT、已应用参数、物理扬声器配置、播放计划）；跳过、结构修正、失败；结束时的完整报告（与 CLI 相同） | 播放器的实时输出与 `PlaybackReport::summary` |

- **请求格式、协商结果与可查询参数分开写**：日志逐条列出请求（`请求 #n：… （描述类型）IsFormatSupported(独占) … Initialize …`）、选定的一条（`← 已协商`）、`已应用参数`（WASAPI 独占流只能读回端点缓冲帧数，格式明确写“不可查询”，不以 `GetMixFormat` 代替）。格式行只写协商结果的摘要。
- **不显示未经证实的 bit-perfect**：完整播放的结论是“严格路径，无欠载、无错误（不证明设备端 bit-perfect）”。
- **欠载、跳过与输出错误实时显示**，出现后保真状态不再是“未改动样本”，结束结论不再是完整保真。
- **丢帧与重复帧**：桌面后端不丢帧也不重复帧（整包后端整包提交，短写后端保留未提交的数据，见 AGENTS §2）。停止与切歌丢弃的是队列中尚未播放的数据，报告为“已中断”或“按操作切换曲目”。所以状态栏没有丢帧计数。
- **设备不支持格式或独占打开失败**：状态栏写明曲目与原因，例如“播放已停止：曲目 1 无法打开输出设备：……”，详细的请求与探测记录在日志中。界面没有共享模式、重采样或音量选项。

## 2. 截图核对的方法

- `qybit-gui` 的 `sim` 特性（只在 CI 中用单独的目标目录编译，发布产物不含）：用 `qy-player` 的假后端代替 WASAPI。播放走真实核心、自有解码、pack 与渲染循环，只模拟设备与时间。假设备按真实时间消费，队列不足时补静音并记为欠载；它不接受单声道（与常见独占端点相同）。由环境变量选择正常、慢速读取（读取限速为码率的 1/4，产生真实欠载）、设备失效（约 2 秒后取缓冲失败）。窗口标题写明“模拟设备，只供界面核对，没有声音输出”。
- CI 的 `gui-windows` 作业依次启动各情形，用 `WM_COMMAND` 发出播放、暂停、下一首、停止，用 `BM_CLICK` 勾选单声道复制。每个状态用 `PrintWindow` 截取窗口，用 `WM_GETTEXT` 读出状态栏第一栏与日志文字，一并写入日志并上传为构建产物 `qybit-gui-shots`。最后一项用发布版连接真实 WASAPI。
- 核对方式：把截图中的格式行、状态栏、保真栏与同一时刻的日志和结束报告逐项对照。

## 4. 核对中发现并已修正的问题

1. **格式行显示了下一首的源格式**：状态原来取“正在解码的曲目”的格式。下一首已预读时，正在播放 44.1 kHz 的曲目却显示“源 96 kHz 24 位 → 设备 44.1 kHz 16 位”，看起来像重采样。改为记录每首曲目解码时的源格式，按正在播放的曲目查找。回归测试 `status_source_follows_playing_track`：严格路径下每个带设备格式的快照，源与设备的采样率、声道数相同；该测试在旧实现上失败。
2. **格式不支持时状态栏只写“详见日志”**：改为写明曲目与原因（`Outcome::stopped`）。
3. **状态栏第一栏被截断**：欠载时“缺 M 帧”被第二栏盖住。格式移到单独一行；未播放时状态栏只有一栏。
4. **暂停标记显示为方框**：系统界面字体没有 U+23F8（⏸）的字形，改用“‖”。CLI 的暂停行同样改用“‖”。

5. **浮点转整数复选框看不到**（2026-10-17 用户真机，界面缩放较大时）：复选框排在工具栏第一行最右，宽度取“剩余宽度”，第一行放不下时变成 0。两个非严格选项改为单独一行，设备下拉框占第一行余下宽度（至多 360）。CI 截图步骤核对两个复选框完整可见、互不重叠。

### 4.1 用户建议的界面调整（2026-10-17）

- **列表与日志区的分隔条**：两者之间有 6 像素（96 DPI）的分隔条，鼠标移上去显示上下箭头，拖动调整日志区高度。列表至少 60、日志至少 40 像素；设定的高度在窗口缩放与 DPI 变化时保持。列宽仍由列标题拖动调整。
- **“查看”菜单**：
  - “显示日志”勾选项：隐藏时列表占满；
  - “清除日志”：只清日志区文字，播放状态、结束结果与之后的新日志不受影响（`qy_ui::Ui::clear_log`）。
- **未保存**：这些设定不写入配置文件，下次启动恢复默认（显示日志、日志占可用高度的 1/4）。
- **验证**：CI 截图步骤核对清除后日志为空、隐藏后不可见、再次显示后可见。分隔条拖动 CI 未覆盖，用户 2026-10-17 在 Windows 真机上确认（含查看菜单的两项）。

## 5. T4：Windows 发布构建

- **产物**：CI 每次推送都上传 `qybit-windows`（`qybit-gui.exe`、`qybit.exe`），单文件，无安装程序。
- **大小**（release，静态 C 运行库）：`qybit-gui.exe` 0.81 MiB，`qybit.exe` 0.73 MiB。
- **C 运行库静态链接**：`.cargo/config.toml` 为 `x86_64-pc-windows-msvc` 设置 `+crt-static`，exe 不依赖 VC++ 可再发行组件包（改前导入 `vcruntime140.dll`，干净的系统上不一定有）。
- **导入的 DLL**（`dumpbin /dependents`）全部是系统组件：
  - `qybit-gui.exe`：kernel32、user32、gdi32、comctl32、shell32、ole32、oleaut32、combase、propsys、avrt、ntdll、api-ms-win-core-synch-l1-2-0；
  - `qybit.exe`：kernel32、advapi32、ole32、oleaut32、combase、propsys、avrt、ntdll、api-ms-win-core-synch-l1-2-0。
- **系统要求**：x64 Windows 10 1607 或更新。PE 头写的是 6.00（Vista），但实际要求更高：Rust 1.97 标准库要求 Windows 10；GUI 静态导入 `GetDpiForWindow`、`SystemParametersInfoForDpi`（Windows 10 1607 起）。没有在更早的系统上运行过。
- **CI 测量**（runner，无 GPU、无音频设备）：启动后空闲 20 秒进程 CPU 0 ms，工作集 21 MiB；正常关闭，退出代码 0。

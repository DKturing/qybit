# QyBit Core 定位与 MCU 场景接口缺口分析

日期：2026-10-13。依据：M0–M2 T4 的代码。§3 的缺口已在 M3 T1 中处理，记录见 [m3-t1-engine.md](m3-t1-engine.md)。

## 1. 定位

**QyBit Core** 是项目的核心产品，桌面播放器只是它的应用之一。定义如下：

> QyBit Core 是基于 Rust 的、`no_std`、无 `alloc`、与操作系统和具体硬件无关的本地音频播放引擎。它负责媒体解析、音频解码、播放状态、流式缓冲调度和 PCM 输出组织，通过统一的宿主接口运行在桌面系统与嵌入式设备上。

Core 可以独立完成播放逻辑，但不能脱离存储和音频输出硬件自己发声。板级宿主负责以下几件事：读取文件字节、提供音频时钟、DMA 和中断、驱动 DAC。

| 能力 | Core | 宿主 |
| --- | --- | --- |
| WAV/FLAC 解析与解码 | ✔（codec crate） | |
| 播放、暂停、停止、换曲、跳过 | ✔ | 把用户输入转成调用 |
| 输入窗口与读请求调度 | ✔ | 执行读取、回报结果 |
| PCM 格式规则、pack、bit-perfect 约束 | ✔ | |
| 输出流调度：预填、排空、换格式、背压、欠载判定 | ✔（**当前缺口**，见 §3.1） | 搬运字节、提供时钟 |
| 存储介质与文件系统（SD 卡、eMMC、U 盘、闪存等）、WASAPI/ALSA/I²S、DMA、中断、线程 | | ✔ |
| GUI、按键、屏幕 | | ✔（应用层） |

成熟度分三层，最终目标是第三层：

| 层次 | 标准 | 现状 |
| --- | --- | --- |
| 编译可移植 | no_std 目标构建通过 | ✔ 核心、codec、pack 都能编译到 thumbv7em |
| 功能可移植 | 同一个 Core 在模拟宿主和 MCU 宿主下完成真实解码、播放与错误处理 | M3 T1 后：调度已下沉到 `qy_core::engine`，模拟、桌面与 MCU 演示共用；MCU 部分只在 QEMU 中运行过（见 [m3-t1-engine.md](m3-t1-engine.md)），实机未运行 |
| 实时可靠 | 真实 MCU 长期运行，资源不超限，没有未报告的欠载，数字输出符合配置 | ✘ 尚未上板 |

## 2. 冻结接口能否表达“MCU 非阻塞读卡 + DMA 播放”

冻结接口指 M0 T4 冻结的 `Action` / `Event` / `Decoder`。逐项检查：

| 场景需求 | 现有接口 | 结论 |
| --- | --- | --- |
| 读卡非阻塞：发出读请求后宿主随时回报，慢读不卡死核心 | `Action::Read{generation, request, max}` → 宿主写入 `read_target()` → `Event::ReadDone/ReadEof/ReadFailed`。核心在等待期间 `poll()` 返回 `None`，不阻塞、不轮询时钟 | **足够** |
| 停止、换曲后丢弃过期的读完成（读卡 DMA 迟到的回报） | `Generation` 加请求号，过期回报被拒绝（M0 T4 已有测试） | **足够** |
| 区分缺输入与 EOF；短读、零长度读 | `ReadDone{len}` / `ReadEof` 分开表示；`Decoder::decode(input, eof)` 返回 `NeedInput` / `End` | **足够** |
| 解码与输出分离，DMA 以固定周期取数 | `Action::Output{frames}` 加 `pcm()`，宿主 pack 后入队，回报 `Event::Output{frames: 实际入队数}`；队列满时回报 0，形成背压 | 接口**足够**；队列与调度见 §3.1、§3.2 |
| 设备格式与源格式的匹配，设备不支持时报错 | `Action::Configure{format}` → `Configured` / `ConfigureFailed` | **足够** |
| 播放、停止、从第 k 首开始 | `Core::play(first, count)`、`Core::stop()` | **足够** |
| 暂停与恢复 | 核心没有暂停状态。暂停期间生产端照常解码到队列满，然后背压等待；宿主停止从队列取数。I²S 必须继续输出时钟，DMA 输出静音 | 不需要改核心接口；**调度层**要区分“暂停静音”和“欠载”（§3.1） |
| 下一首、上一首、出错后跳过坏文件 | `stop()` 后 `play(k±1, count)`；`Action::Failed{track, fault}` 之后由宿主决定是否从 `track+1` 继续 | 接口**足够**；跳过策略属于调度层 |
| 资源能力声明（最大采样率、声道、位深、FLAC 块大小、输入窗口） | 只有 `qy_codec_flac::Capacity`，没有统一的查询入口 | **缺口**，可以**新增**，不破坏现有接口（§3.3） |
| 解码出错的明细 | `DecodeError`（4 类，冻结）；FLAC 明细通过 `flac_error()` 获取 | **足够** |

**结论**：冻结的 `Action` / `Event` / `Decoder` 已经足以表达 MCU 的非阻塞读卡与 DMA 播放，**不需要破坏性变更**。缺口都在核心之外，或者可以作为新增 API 补上，详见下一节。

## 3. 缺口

### 3.1 播放调度在 std 层（最主要的缺口）

以下逻辑目前都在 `qy-player::player` 中，依赖 `std::fs::File`、线程、`Arc` 和 `Vec`：

- 预填 500 ms 后才启动设备；
- 新格式能被当前设备格式无损承载时继续用当前流，否则先排空再重开；
- EOF 和失败时排空已入队的有效音频；
- 背压等待、设备错误后停止核心；
- 报告组织。

MCU 宿主无法复用这些逻辑，只能另写一套。这正是“桌面和单片机共用同一个播放核心”要避免的局面。

**需要的改动**：把调度抽成 `no_std`、无 `alloc` 的状态机，可以放进 `qy-core` 的新模块，或单独做一个 crate。

- 输入：核心动作、宿主回报、队列水位、设备状态。
- 输出：要宿主执行的操作，即打开/读取/配置设备、启动/停止输出、排空完成等。
- 暂停、下一首、出错跳过的策略也在这一层。
- 暂停期间 DMA 输出的静音单独计数，不算欠载。

完成后，`qy-player`（桌面）、`qy-host-sim`（模拟）和 MCU 宿主都只负责“读字节、搬字节、报告设备事件”。验收标准：模拟宿主改用新调度层后，WAV 1000 个种子和 FLAC 1200 个种子的场景结果逐字节不变。

### 3.2 设备帧队列需要 alloc

`qy_pcm_format::ring` 基于 `rtrb`，在堆上分配。MCU 需要放在静态内存里的成熟 SPSC 队列。AGENTS 禁止自己写无锁缓冲，因此要从成熟库中选型，并锁定版本：

- `bbqueue`：按连续区域分配和提交，适合 DMA 直接读取一段连续内存；
- `heapless::spsc`：按元素入队/出队。

选型在 M3 T1 中进行，需要核对版本、`no_std` 支持、`unsafe` 边界和中断中的使用方式。桌面仍可继续用 `rtrb`；两种实现放在同一个“按完整帧入队、出队”的接口后面。

### 3.3 资源能力声明与配置档

需要新增一个统一的能力描述，例如 `Capabilities { max_rate, max_channels, max_bits, flac: Option<Capacity>, input_window, queue_bytes }`：

- 宿主启动时声明能力，核心据此在 `Configure` 之前拒绝超出能力的源，并给出明确错误；
- 配置档（Desktop / Embedded Lite / Embedded Full）是同一套代码的不同常量，不是两套实现；
- 实际支持的 FLAC 帧大小、最低 RAM 和实时解码余量，必须在指定 MCU 上**测量**后写入任务卡，不能估算。

### 3.4 codec 按需链接

`qy-codec-auto` 现在总是同时链接 WAV 与 FLAC。需要加 feature：`wav`、`flac`，默认都开。只用 WAV 的 MCU 可以不链接 FLAC。这是新增改动，不破坏现有接口。

### 3.5 不改动的部分

- **crate 依赖方向已经正确**：`Decoder` 契约在 `qy-core`，codec 依赖 core，core 不依赖 codec，`qy-codec-auto` 负责组装。
- **目录重组为 `apps/`**：只是外观调整，收益低，暂不做。

## 4. 路线调整

已经得到用户同意（2026-10-13）：

1. M2 T5（验证加强）延后。
2. 新增 **M3：QyBit Embedded Reference**，见 `tasks/M3.md`。
   - T1 是不依赖硬件的核心下沉：no_std 调度、静态队列、能力声明、codec feature，用模拟宿主验收。
   - T2 做不绑定开发板的通用嵌入式宿主（板载存储读取，介质不限；I²S DMA 输出；串口控制），板级只做薄适配；实时性与数字输出采集需要在用户手头任一满足最低要求的实物板上运行（2026-10-13 用户确认不指定开发板）。
3. GUI 仍然排在最后，作为薄应用层。

## 5. 确定性约束（R1 §5）

QyBit Core 承诺四个约束。下表写明每项由哪些检查保证、只在什么范围内成立。R1 的数值与运行记录见 [r1-reliability.md](r1-reliability.md)。

| 约束 | 含义 | 由哪些检查保证 | 成立范围 |
| --- | --- | --- | --- |
| 内存 | 播放所需内存不超过配置档预算 | 配置档预算公式与独立核对（`Profile::budget`，M3 T1）；播放前的资源计划：超出声道、位深、采样率、FLAC 最大块、声明最大帧或队列容量时按能力不足拒绝并给出数值（R1 §1）；MCU 链接段 `.bss` 核对与栈涂色高水位（QEMU） | 预算公式覆盖的缓冲；栈高水位只是 QEMU 中所跑路径的观测值，不是上界证明 |
| 时间 | 生产端在输出截止时间前备好数据 | M3 T2 预填与负载公式（`budget`）；水位统计：最低水位、低水位与临界次数，欠载单独计数（R1 §2）；虚拟时间仿真与模型随机测试中“声明以内无欠载”；桌面端到端基准（R1 §6）；M3 T3 实物长时运行 | 只对指定的硬件、格式与存储时序成立：仿真只证明公式与调度在声明时序下自洽；桌面基准只对记录中的机器成立；MCU 的实时性要到 M3 T3 实测，不推广为“所有环境” |
| 保真 | 无损表示归一化后，输出等于参考样本 | 自有解码器与独立参考（ffmpeg、libFLAC、手写码流）逐样本比对；pack 往返配独立参考字节；模拟回归摘要（WAV 1000、FLAC 1200 种子）；模型随机测试的整帧前缀检查；A 层逐字节回环；桌面端到端基准逐字节比对 | 软件路径。类型标记与回环不证明设备端 bit-perfect；真实 DAC 的数字输出要到 M3 T3 采集 |
| 零分配 | 进入播放状态后不发生动态分配 | 核心与 codec 为 `no_std` 无 `alloc`；桌面宿主启动时一次性分配并有不重分配测试；MCU 全部静态分配（`.bss` 核对） | 核心、codec、pack 与宿主的播放路径；平台 API 内部（WASAPI、ALSA）的行为不在此列 |

几点说明：

- 四个约束互相独立：发生欠载时内存与零分配约束仍然成立，但这一段不能再称为完整保真（AGENTS §3）。
- 文件头声明不可信：资源计划用文件头给出提前、带数值的原因；逐帧边界检查仍在解码器里，帧超出声明或容量时按解码错误报告。
- 损坏的存储结构是不可信输入：FAT 结构在交给 FAT 库之前按规范独立核对（R1 §4），不合格的文件跳过并计数，不 panic、读取量有上界。

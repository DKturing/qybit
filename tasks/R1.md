# QyBit R1：资源计划与可靠性验证

遵循根目录 AGENTS.md。前置：M3 T2 不需要硬件的部分完成。

状态：已完成，记录见 [docs/r1-reliability.md](../docs/r1-reliability.md)。全部为模拟、虚拟时间仿真、fuzz、QEMU 与开发机结果，不是实机结果。顺序：用户确定排在 M3 T3（实物长时运行与数字输出采集）之前（2026-10-14）。本卡不需要硬件。

**目标**：在上实物之前，把“能不能播、为什么不能播、播的时候余量多少、各种操作组合下会不会出错”都变成可核对的结果：

1. **资源计划**：播放前给出完整、统一、带具体数值的可行性判断；
2. **缓冲水位统计**：运行时记录实时余量，作为 T3 的直接证据；
3. **基于模型的随机命令测试**：大量随机操作与故障组合下的不变量检查；
4. **损坏文件系统 fuzz**：处理 M3 T2 审阅中发现的 `embedded-sdmmc` panic 风险；
5. **确定性约束的统一表述**：把已有的各项检查归到四个约束下，写入文档；
6. **桌面吞吐基准**：实测解码的实时倍数与高规格端到端余量，作为 P1 的依据（用户 2026-10-14 加入）。

本卡不改变样本、不改变播放语义；冻结的 `Action` / `Event` / `Decoder` 不变。实现中如果发现必须破坏冻结接口，先停下来征得用户同意。

## 1. 资源计划（播放前的可行性判断）

**现状与问题**：拒绝原因因格式而异。

- 6 声道 WAV 在 Embedded 上由引擎能力检查拒绝，报 `Capability(Channels { channels: 6, max: 2 })`；
- 6 声道 FLAC 在 STREAMINFO 处由解码器容量拒绝，只报 `Core(Decode(CapacityExceeded))`；
- FLAC 块大小超出本机容量时同样只有 `CapacityExceeded`，不说明是哪项、超出多少。

**要求**：

- 文件头解析完成后、打开设备之前，按统一规则核对源对本机资源的需求，给出**带数值的具体原因**。例如：
  - “6 声道超出本机配置的上限 2 声道”（WAV 与 FLAC 一致）；
  - “FLAC 最大块 8192 帧超出本机配置的 4608 帧”；
  - “FLAC 32 位超出本机解码容量 24 位”；
  - “本机配置的队列不足以承载 384 kHz / 8 声道 / C32”。
- 这些原因归入能力不足（`EngineFault::Capability`），与采样率、声道、位深的现有检查同一类别、同一报告格式。
- **文件头声明不可信**（RFC 9639 安全注意事项）：
  - STREAMINFO 声明的最大块、声道、位深只用于提前给出原因；
  - 逐帧的边界检查照旧保留，帧超出声明或容量时仍按解码错误报告；
  - 用夹具覆盖“STREAMINFO 声称小块、实际帧更大”的情形。
- **播放计划**：可播放时，报告写明计划。内容包括：
  - 设备格式；
  - 预填帧数与时长；
  - 队列占用；
  - 输入窗口与解码工作区的需求 / 容量（例如 FLAC 最大块 4096 / 4608）。
  
  桌面报告、模拟报告与嵌入式 `status` / 通知都包含这些内容。
- **接口**：
  - 解码器的需求经一个**新增的**查询接口提供（例如引擎侧的需求 trait 或解码器的明细查询），不改冻结的 `Decoder`；
  - 引擎不是冻结接口，可以调整其泛型约束；
  - 具体形式在实现时决定并记录理由。

**验收**：

- Embedded 配置下：
  - 6 声道 WAV 与 6 声道 FLAC 报告同一类原因；
  - 块大小、位深超限的 FLAC 报告具体数值；
- 桌面配置下这些文件照常播放；
- STREAMINFO 不实的夹具仍在帧级被拒绝，不 panic；
- **回归**：WAV 1000 种子与 FLAC 1200 种子的逐种子摘要不变（摘要不含拒绝原因，或按规范依据说明变化并保留回归覆盖）；
- 已有测试中期望 `CapacityExceeded` 的地方改为新原因时，逐项写明依据。被改的测试至少包括 `sim_multichannel` 与 MCU 演示。

## 2. 缓冲水位统计

**要求**：

- 消费端每次取数前记录队列中的帧数，统计：
  - **最低水位**：帧数与对应毫秒数；
  - **低水位次数**：低于预填量的一半；
  - **临界次数**：低于 2 个输出周期（DMA 缓冲或渲染包），即下一次取数可能不够；
  - **欠载**：照旧单独计数。
- **只观测，不改调度**。MCU 主循环是单线程，读取与解码本来就按顺序进行，没有可调的优先级。
- 中断与音频回调里只增加常数次比较与计数：有界、不分配、不阻塞。
- 覆盖范围：
  - MCU 喂数器（`qy-host-embedded`）；
  - 桌面短写与整包渲染循环（`qy-player`）；
  - 模拟宿主。
- 报告位置：
  - 嵌入式：`status` 行；
  - 桌面：播放报告；
  - 模拟：报告；
  - QEMU 演示：报告行。
- 阈值写入代码常量并在文档说明；不改变任何样本。

**验收**：

- 虚拟时间仿真中：
  - 时序在声明以内时，最低水位高于临界线；
  - 注入超过预填的停顿时，先出现临界计数，再出现欠载；
  - 各种子的数值是确定的，并记录在文档中。
- 桌面假设备与 A 层回环的报告包含水位。
- 已有的逐字节结果不变。

## 3. 基于模型的随机命令测试

在 M3 T2 的虚拟时间仿真（`qy-host-embedded/tests`）上，用种子生成随机序列。

**随机内容**：

- 操作：`play n`、`pause`、`resume`、`stop`、`next`、`prev`、`status`、`ls`、`scan`、错误命令与超长行，在随机的虚拟时刻经串口行缓冲送入；
- 故障：第 k 次块读取失败、周期性停顿（在声明以内或超出）、拔卡与重新插卡；
- 播放列表：
  - 夹具：WAV / FLAC、能力不足、解码错误；
  - 合成的较长曲目；
  - FAT 与无文件系统两种存储。

**每个种子都检查的不变量**：

- 不 panic，主循环在时限内结束；
- 每个输出段的有效数据都是某首曲目参考字节的**前缀**；
- 段与段之间按播放顺序，既不重复也不串曲。“下一首”“上一首”“跳到第 n 首”后的曲目，要符合按播放位置推算的期望；
- 时序在声明以内且未注入超出预填的停顿时，欠载为 0；
- 暂停期间不取数（暂停静音单独计数）；
- 各计数自洽：
  - 跳过数等于 `skip` 通知数；
  - 读取错误数等于注入并实际命中的次数；
  - 协议错误与喂数错误为 0；
- 停止后、播放结束后，`status` 显示 `stopped`。

**规模与记录**：

- 种子数与虚拟时长写入记录：至少 500 个种子，每个至少覆盖 20 次操作。
- 失败的种子输出可复现的操作序列，修复后加入固定回归集。
- 本卡不要求实现自动缩减（shrinking）。

**验收**：

- 全部种子通过；
- 变异检查，逐一改坏后能被发现。至少改坏这四处：
  - 排空判定；
  - 暂停取数；
  - 切歌时的代次检查；
  - 读取错误计数。

## 4. 损坏文件系统 fuzz

M3 T2 审阅发现：`embedded-sdmmc` 0.10.0 的读取路径中有 `assert!` / `panic!`，例如 `next_cluster` 对越界簇号 panic，损坏的 FAT 可能触发。这属于不可信输入，按 AGENTS §4 不得 panic。

**要求**：

- 新增 fuzz 目标：以有效的 FAT16/FAT32 镜像为初始语料，对 MBR、引导扇区、FAT 表、目录项与数据区做变异；
- 运行 `FatStorage` 的扫描、打开、读完全部曲目与重新扫描；
- 检查：
  - 不 panic；
  - 不越界读取；
  - 读取总量有上界，不因 FAT 环路无限读取；
  - 错误都以 `Err` 返回。
- 发现 panic 后，按以下顺序处理：
  1. 在 `FatStorage` 或块设备层加防护（例如目录项簇号、文件长度与卷大小的范围检查，簇链长度上限）；
  2. 防护不了的，记录并向上游报告；
  3. 必要时评估改用其他成熟 FAT 库（先征得同意）。

**验收**：

- fuzz 至少 10 分钟，种子与结果写入记录；
- 发现的问题都有回归用例；
- CI 加入 60 秒冒烟。

## 5. 确定性约束的统一表述

在 `docs/arch-core-mcu.md` 中写明 QyBit Core 的四个约束，以及每项由哪些检查保证、只在什么范围内成立：

| 约束 | 含义 | 现有或本卡的检查 |
| --- | --- | --- |
| 内存 | 播放所需内存不超过配置档预算 | 配置档预算公式与独立核对；资源计划（本卡）；链接段 `.bss` 核对 |
| 时间 | 生产端在输出截止时间前备好数据 | M3 T2 预填与负载公式；水位统计（本卡）；T3 实物长时运行 |
| 保真 | 无损表示归一化后，输出等于参考样本 | 逐字节回环、模拟回归摘要、独立参考比对 |
| 零分配 | 进入播放状态后不发生动态分配 | 核心与 codec 无 alloc；桌面宿主不重分配测试；MCU 全部静态分配 |

时间约束只对指定硬件、格式与存储条件成立，不推广为“所有环境”。

## 6. 桌面吞吐基准

**目的**：桌面的队列与预填已按公式分配，但解码速度和读盘延迟没有实测。高规格（如 384 kHz / 24 位 / 8 声道 FLAC）能否实时、余量多少，需要数据。

**要求**：

- **解码实时倍数**：release 构建，在开发机上逐格式、逐规格测量“解码 + pack”的吞吐，记录为实时倍数（每秒处理的音频秒数）。
  - 规格至少覆盖：WAV 与 FLAC 各 44.1/96/192/384 kHz、16/24/32 位、双声道与 8 声道（FLAC 另含块 4096 与 16384、固定预测与 LPC 32 阶）。
  - 测试文件由夹具生成器按固定种子生成，内容确定。
  - 只计时解码器与 pack，不含磁盘读取与设备输出。
  - 每项至少重复 5 次，取最慢一次作为结果，同时记录中位数。
- **端到端余量**：高规格文件经真实的播放器层（`qy-player`）、引擎、解码、pack、队列与渲染循环，接到假设备（按真实时间消费），配合 §2 的水位统计，记录最低水位与临界次数。
  - 规格：WAV 768 kHz / 32 位 / 双声道；FLAC 384 kHz / 24 位 / 8 声道（队列允许的上限附近）。
- **读盘延迟的影响**：在假文件层注入读取延迟与停顿，确认队列余量足以覆盖，或在余量不足时由水位统计如实报告（不追求通过，只要求如实）。
- **记录**：
  - CPU 型号、核数、频率策略、操作系统、编译选项；
  - 结论只对记录中的机器成立。

开发机的结果不能代表用户设备，也不能代表 MCU；MCU 的实时性仍由 M3 T3 实测。

**验收**：

- 基准可重复运行：命令写入文档，结果表格写入记录；
- 端到端用例在 CI 中以缩短的时长运行，只检查不 panic、逐字节一致、计数自洽，不检查性能数值（CI 机器性能不稳定）；
- 结论列出达不到实时或余量很小的规格，作为 P1 第 3 项（解码内核优化）的启动依据。

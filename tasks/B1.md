# QyBit B1：边界整理（核心不认格式、可选策略隔离、最小配置可组装）

遵循根目录 AGENTS.md。来源：2026-10-16 外部架构评估（结论：保留核心骨架，做一次有回归测试保护的边界收紧）。代码核对见 §1。顺序：可靠性修复（[docs/fixes-2026-10-16.md](../docs/fixes-2026-10-16.md)）之后，B1 → L1（[L1.md](L1.md)）→ X1（[X1.md](X1.md)）。

状态：**已完成**（2026-10-17；§6 两项均按建议）。完成记录、尺寸与验证见 [docs/b1-boundaries.md](../docs/b1-boundaries.md)，与本卡的差异见 §8。

**目标**：新增一种 codec 时只写 codec 本身（接口实现、资源需求、诊断）并在组装层接入，不修改播放状态机；只含 WAV 的配置能在桌面与 MCU 上组装。**行为不变**：所有现有测试（含模拟、QEMU 与 A 层回环的逐字节核对）照常通过，报告的中文含义不变（措辞可调整）。

## 1. 现状（2026-10-17 核对 `afe44ad`）

- **核心认识 FLAC**：
  - `qy-core/src/engine.rs` 的 `CapabilityError` 有 `FlacBlock { block, max }` 与 `FlacFrame { bytes, window }`，`Display` 直接写“FLAC 最大块……”；
  - `DecoderDemand` 的字段是 FLAC 的块与帧（`max_block`、`block_capacity`、`max_frame`、`window`），`PlaybackPlan` 的文字写“FLAC 最大块 …/… 帧，最大帧 …”。
- **可选策略散在状态机中**：单声道复制（O1，`ChannelPolicy`）与浮点转整数（F3，`FloatPolicy`、转换工作区、回退阶段、拒绝记录、报告）在 `engine.rs` 中约 68 处引用，分布在配置、请求设备、入队、报告等路径。
- **组装绑定 FLAC**：`qy-player` 的 `HostResources::with_profile` 第一行要求 `profile.flac_capacity()`，没有 FLAC 的配置档返回 `HostError::Profile`；`AutoDecoder::new` 一次性要求 WAV、FLAC 两份工作区。嵌入式已用 `AutoDecoder::empty().with_wav()...` 按需组装（M3 T1），桌面没有。
- **缓冲所有权**：大缓冲经 `&'static mut` 由宿主启动时一次取得（桌面 `Box::leak`），换曲复用。长期运行的播放器没有问题；但反复创建并销毁 `HostResources` 会持续泄漏，这一点没有写在文档里。

## 2. 核心只表达资源，不表达格式

- **`CapabilityError`**：用与格式无关的两项替换 `FlacBlock` / `FlacFrame`：
  - `DecodeUnit { frames, max }`：源声明的最大解码单元（帧数）超出本机解码容量；
  - `InputUnit { bytes, window }`：源声明的最大输入单元（字节）超出本机输入窗口。
  - 核心的 `Display` 只写资源（“最大解码单元 4608 帧超出本机配置的 1152 帧”）；FLAC 的说法（“最大块”“最大帧”）由 codec 提供的诊断或宿主报告补上。
- **`DecoderDemand`**：字段改为 `max_unit_frames`、`unit_frames_capacity`、`max_unit_bytes`（0 表示未声明）、`window`；`PlaybackPlan` 的文字改为“解码单元 …/… 帧，输入单元 …/… 字节”。
- **codec 的名称与术语**：`Resources` 新增带默认实现的 `fn codec(&self) -> Option<&'static str>`（如 `"FLAC"`），宿主报告据此写“FLAC 最大块”；核心不使用它。
- **不做**：不在核心增加列举全部格式的枚举；格式注册与详细诊断留在 `qy-codec-auto` 与应用组装层。

## 3. 可选策略隔离

- 把单声道复制与浮点转整数的状态和判断从 `Engine` 的各处分支收进 `qy_core::engine::options`（暂名）中的一个结构，例如 `Options { channel, float, convert_ws, stage, rejected, … }`。对引擎只暴露少数几个调用点：
  - 呈现：源格式 → 请求格式（O1 的 `[FC] → [FL FR]`、F3 的整数回退阶段）；
  - 失败回退：设备拒绝时是否改请求下一档；
  - 入队：是否经转换；
  - 报告：每首第一次入队时的通知、关闭时的统计。
- 只是内部重构：公开方法（`set_channel_policy`、`set_float_policy`、`set_convert_workspace` 等）不变，行为与报告不变。
- 验收看结构而不是行数：两项选项的全部状态都在该结构中，状态机的其余部分只经上述调用点使用它；新增第三项选项时，按这几个调用点即可接入。

## 4. 最小配置可组装

- **`qy-player`**：
  - `HostResources` 增加按需组装的构造（`builder()` 或明确的构造函数），各项可选：WAV（含 AIFF 共用工作区）、FLAC（容量）、浮点转换工作区、队列大小；
  - `with_profile` 按配置档有无 FLAC 自动选择，不再要求 FLAC；
  - `qy-player` 增加默认开启的 `flac` 特性，透传到 `qy-codec-auto`。
- **必须能构建并通过测试的组合**：
  1. WAV-only（`qy-player --no-default-features`）；
  2. WAV + FLAC（默认）；
  3. 不含浮点转换工作区；
  4. 无 GUI（CLI 与库）；
  5. MCU 静态资源（Embedded Full / Lite，现有）。
- **文档**：在 [docs/arch-core-mcu.md](../docs/arch-core-mcu.md) 写明 `&'static mut` 缓冲的所有权模型，以及“反复创建并销毁实例不会回收这些缓冲”的限制。可回收所有权以后作为通用库需求时再单独讨论，本卡不改接口。

## 5. 验收

1. `qy-core` 中不再出现 FLAC 专有的类型、字段与文字（`grep -i flac crates/qy-core/src` 只剩注释中的历史说明或为零）。
2. 报告与界面文字：FLAC 曲目的拒绝原因与播放计划仍写明“FLAC 最大块 / 最大帧”。由宿主经 `codec()` 补上，测试核对原文。
3. §4 的五种组合在 CI 中构建；WAV-only 组合运行 `qy-player` 的测试子集（WAV / AIFF 夹具），FLAC 曲目按“不支持”拒绝并说明原因。
4. 行为不变：
   - 全部现有测试通过，含模拟场景、500 个模型随机种子、QEMU 演示与 A 层回环的逐字节核对；
   - `.text` 与 RAM 预算变化记录在案（预计很小）。
5. no_std（thumbv7em）构建与 Clippy；fuzz 目标照常编译，CI 冒烟通过。

## 8. 实施中的差异（2026-10-17）

1. §2 的 `Resources::codec()` 没有新增：跳过曲目时，宿主格式化错误之前引擎可能已为下一首复位解码器，届时问到的格式不对。改为由解码器随错误与需求给出单元叫法（`engine::Unit { codec, name }`，`CapabilityError::DecodeUnit` / `InputUnit` 与 `DecoderDemand` 各带一个），验收 2 的“FLAC 最大块 / 最大帧”原文照旧由测试核对。
2. 单元以 `&'static Unit` 携带：按值携带使 `FlacDecoder` 超出 448 字节的结构体大小上限。
3. 嵌入式串口播放计划事件的字段改名为 `decode_unit=` / `input_unit=`。
4. 为验收 3 新增 `DESKTOP_WAV` 配置档与 `AutoDecoder::disabled()`（报告“本构建未启用 FLAC 解码器，按不支持拒绝”）。
5. `Unit` 用手写 `Debug`：派生的版本会链接 `str` 的转义格式化（MCU 上约 3.7 KB）。

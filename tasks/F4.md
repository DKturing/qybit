# QyBit F4：WAV RF64 / BW64（64 位长度）

遵循根目录 AGENTS.md。顺序见 [tasks/FORMATS.md](FORMATS.md)：基础格式，F3 之后。

状态：**软件部分已完成**（2026-10-18），记录见 [docs/f4-rf64.md](../docs/f4-rf64.md)。已按用户提供的 BS.2088-2 原文逐条核对并更正三处（见记录 §2）；真实设备未运行。

**目标**：`qy-codec-wav` 读取 RF64 与 BW64 文件，支持超过 4 GiB 的 WAV（长时间的高采样率或多声道录音）。样本编码、fmt、声道布局、浮点与 W1 容错规则与普通 RIFF/WAVE 完全相同；只是长度改由 `ds64` 块给出。严格路径不改变样本。

## 1. 结构

- **文件头**：`RF64` 或 `BW64` + 4 字节长度 + `WAVE`。按规范，RF64/BW64 的 32 位 RIFF 长度字段为 0xFFFFFFFF（“不使用，见 `ds64`”）；该字段不携带信息，**不使用也不报告**。
- **`ds64` 块**：必须是 `WAVE` 之后的第一个块，否则不合规。
  - 体长度 ≥ 28：riffSize（u64）、dataSize（u64）、sampleCount（u64）、tableLength（u32）；
  - 其后 tableLength 个表项，每项 12 字节：块标识（4 字节）+ 64 位长度；表项总长不得超过块长度，否则不合规；表之后的剩余字节跳过；
  - `ds64` 只能出现一次。
- **RIFF 长度**：以 `ds64.riffSize` 为准，按 W1 的规则处理（R3：与源实际长度不符而 data 完整时以 data 为准，报告修正）。
- **`data` 与 RIFF 长度**（BS.2088-2 §2.4）：32 位字段为 0xFFFFFFFF 时用 `ds64` 的 64 位值；不是时用 32 位值（2026-10-18 按原文更正：原卡要求两者相等）；
  - 其后照常适用 W1 的 R4（不足一帧的尾部）与 R5（源比声明短）。
- **其他块的长度为 0xFFFFFFFF**：按块标识在 `ds64` 表中依次取未用过的同名表项；没有对应表项时不合规。表项按固定容量存放在解码器结构内（不分配内存）；表项超过容量且后面确实需要查表时，按资源不足拒绝并写明容量与所需，不静默出错（AGENTS §3）。
- **`fact` 块**（浮点，F3 规则）：RF64 中 32 位值为 0xFFFFFFFF 时用 `ds64` 的第三个 64 位值（BW64 中它是 dummy，读取时忽略，BS.2088-2 §4.2），再按 F3 核对（必须等于 data 的完整帧数）；PCM 照旧不核对 `fact`。没有 `fact` 块时不核对 `ds64.sampleCount`（它是 `fact` 帧数的 64 位版本）。
- **流式写入程序的占位值**（ffmpeg 输出到管道）：`ds64.riffSize` = 0 视为 RIFF 长度占位（同 W1 R1）；此时 `data` 为 0xFFFFFFFF 且 `ds64.dataSize` = 0 视为 data 长度占位（同 W1 R2），读到源末尾；两者都报告修正。`ds64.riffSize` ≠ 0 而 `dataSize` = 0 时按声明为空的 data 处理。
- **BW64 的其他块**（`axml`、`chna` 等 ADM 元数据）与未知块一样跳过。声道布局只按 fmt 判断（F1）：多于 2 声道而没有 EXTENSIBLE 声道掩码的照旧按“布局未定义”拒绝。
- **普通 RIFF 中的 `ds64` 或 `JUNK` 占位块**：按未知块跳过。

## 2. 实现要求

- 内部的块长度、剩余字节、RIFF 余量、data 起点与定位改为 64 位；所有算术用检查过的运算，不可信输入不 panic。
- `qy_core::engine::Repair` 的 `declared` 字段由 `u32` 改为 `u64`（64 位声明长度的修正也能如实报告）；`WavDetail::DataShort` 同样改为 64 位。
- 新明细 `WavDetail::Ds64`：`data` 两处长度矛盾、缺少表项、表项超过容量（含容量与所需），文字写明原因。
- 解码器仍为 `no_std`、无 alloc；结构体大小增量记录（表项容量 × 12 字节）。
- 文件扩展名：桌面文件筛选增加 `rf64`、`bw64`（多数文件仍为 `.wav`）。

## 3. 夹具与参考

- **生成器**（`tools/qy-gen-fixtures`）独立构造 RF64 / BW64 夹具与期望样本；ffmpeg 作为第二参考逐样本比较（ffmpeg 能读的情形）。
- **覆盖**：
  - RF64 与 BW64，16/24/32 位 PCM、EXTENSIBLE、浮点（带 `fact` = 0xFFFFFFFF）；
  - `ds64` 带非空表、表之后有剩余字节；`data` 之前有 32 位长度为 0xFFFFFFFF、按表取长度的未知块；
  - `data` 的 32 位字段等于 `ds64.dataSize` 的情形；
  - 流式占位（ffmpeg 管道输出的结构）；RIFF 长度不符（R3）；不足一帧的尾部（R4）；源比声明短（R5）；
  - 拒绝：`ds64` 不在第一个、`ds64` 过短、表越界、重复 `ds64`、`data` 两处长度矛盾、缺少表项、表项超过容量、浮点 `fact` 与 `ds64.sampleCount` 不符；
  - **超过 4 GiB 的声明长度**：不写出大文件，用“声明 > 4 GiB、源截断”的夹具核对 64 位长度的解析与 R5 明细，再在测试中流式生成一个超过 4 GiB 的 RF64 源（生成器按需产生字节，不落盘），核对帧数、末尾样本与定位。
- ffmpeg 生成的真实 RF64 文件（可定位输出与管道输出各一个）作为回归样例。

## 4. 验收

1. 全部夹具与独立参考逐样本一致；ffmpeg 能读的与第二参考一致；拒绝情形的类别与明细与期望相同；
2. 任意分块（1 字节、随机、整块）结果相同；`qy-testkit` 契约测试覆盖 RF64；
3. 超过 4 GiB 的流式源：总帧数、末尾样本、定位到 4 GiB 之后的位置都正确；
4. fuzz：`wav_decode` 与 `auto_decode` 语料加入 RF64 / BW64 种子，冒烟运行并记录次数；
5. Kani：文件头与 `ds64` 解析在任意字节下不 panic（更新现有证明并新增 `ds64` 证明）；
6. 模拟宿主：RF64 曲目与普通 WAV、FLAC、AIFF 混排，设备字节逐字节等于独立参考；
7. no_std（thumbv7em）构建与 Clippy；三个配置档预算不变（或记录增量）；QEMU 演示照常通过；
8. 文档 [docs/f4-rf64.md](../docs/f4-rf64.md) 记录规范出处、规则、真实样例核对与已知限制；规范原文核对待用户提供 PDF 后补做。
